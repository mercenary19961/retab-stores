## E-commerce Requirements & Decisions (client brief — 2026-06-29)

> Captured from the client brief. **Reference implementation:** `c:\Users\sabba\Desktop\projects\hardrock-ecom-demo\` — a mature Laravel 12 + Inertia **v2** e-commerce backend we built that ALREADY implements OTO shipping, Tamara, coupons, order activities, admin activity-log/undo, optimistic locking, roles (admin/editor), bilingual AR/EN, and notifications. Retab **adapts** these into a **tighter** build (gateway abstractions, thin controllers + service layer, explicit order state machine). Read hardrock-ecom-demo's files for proven patterns before building (e.g. `app/Services/Shipping/*`, `app/Services/Payments/*`).

### Payments — DECIDED
- **Cards via Moyasar** (mada + Visa/MC + Apple Pay + STC Pay) **+ Tamara (BNPL)** **+ bank transfer** (manual transfer to the store's **Al Rajhi** IBAN, **admin-verified** — added 2026-06-30 to match the client's current site). **No COD, no cash** — every order is prepaid (online gateway or verified bank transfer).
- **Store entity + bank** (from client): legal name **شركة مصنع رطاب الوطن للتمور**; Al Rajhi IBAN `SA9780000145608010008130` (acct `145608010008130`). Stored in `settings` (`bank_*`, `legal_name`); the IBAN is a public receiving account (fine to display).
- Both sit behind a `PaymentGateway` interface (mirror hardrock's `ShippingGateway` pattern); Tamara reuses hardrock's `TamaraClient`.
- **Capture model — DECIDED (hybrid per method):**
  - **Cards (Moyasar) = immediate capture** at checkout; **refund** on customer-cancel or admin-reject. Deliberately avoids any Moyasar delayed-capture dependency.
  - **Tamara = authorize at checkout, capture on admin confirmation**; **void** the authorization if cancelled/out-of-stock (Tamara supports auth→capture natively).
  - Both expose `authorize / capture / void / refund` via the `PaymentGateway` interface; the order flow calls the right one per method + state.
  - SLA: admin confirms within ~24–48h (Tamara auth expires); dashboard flags orders nearing auth-expiry.
  - ⚠️ Trade-off: rejected **card** orders incur a real refund (fee + "money in/out" UX) — acceptable while out-of-stock rejections stay rare (depends on inventory accuracy / أسماك sync); revisit (cards→delayed capture, if Moyasar supports it) if they become common.

### Shipping — DECIDED
- **OTO (Tryoto) aggregator** for fulfillment (reuse hardrock `ShippingGateway`→`OtoGateway`/`OtoClient` + `OtoWebhookController`). **GCC countries only. No Aramex, no DHL** (filter out).
- **Customer pays a SINGLE FIXED flat shipping price** across all GCC, regardless of OTO's actual carrier cost (DECIDED — client accepts absorbing the cross-GCC cost difference). One configurable number in admin.
- OTO **does** return live per-carrier rates via `checkOTODeliveryFee` (POST origin/destination/weight; auth = refresh-token→access-token, cached). Used **internally** for cost/carrier selection — NOT shown as the customer price.

### Products & Inventory — DECIDED
- **Inventory tracked by quantity (units in stock).** Weight is **descriptive only** — shown in the product title/description per product, NOT a structured field (shipping is flat, so weight never drives cost).
- **No variants (DECIDED)** — each sellable item = one product = one SMACC SKU (keeps the Excel import 1:1). All stock is unit-quantity on the product.

### Coupons — DECIDED (+ one POSTPONED)
- Admin-controlled coupon system (reuse + extend hardrock's `Coupon`).
- **Review reward — BUILT 2026-07-29** (a second earn-a-coupon path alongside the 5-purchases loyalty reward): a verified buyer who posts a review **with a comment** earns a **one-time** percentage coupon (admin picks 10% or 20%), account-bound, valid 30 days. `App\Services\ReviewRewardService` mirrors `LoyaltyService`; **off by default** and managed on `/admin/discounts` (`review_reward_enabled` / `review_reward_percent` settings). Once-ever per customer is enforced by the `loyalty_rewards` unique key `(user_id, type='review', threshold)` — ⚠️ `threshold` is meaningless for this type but the key needs a value, so it's stored as `0`. Issuing is row-locked + idempotent (safe on the review-submit path). A **post-delivery WhatsApp nudge** (`SendReviewReminder`, dispatched with a 1-day delay from `ShippingService` on delivery) invites the review; eligibility is re-checked **at send time** and `orders.review_reminder_sent_at` stops a repeated "delivered" webhook re-sending it.
- ⏸ **POSTPONED — QR-code coupons redeemable at the PHYSICAL store** (client used to issue a QR after 5 purchases for an in-store discount). Design later: signed **single-use** token, atomic redemption (optimistic locking), validated either by أسماك or a standalone cashier "redeem" web page (decoupled from أسماك). Revisit after core build.

### Order flow (client's required flow)
1. Customer orders → pays (prepaid) → payment confirmed.
2. Admin notified via **email + WhatsApp + admin-panel notification**.
3. Admin/editor checks inventory & issues, then **confirms**:
   - **If unavailable:** button to WhatsApp the customer (apologize + suggest similar products + "back soon"); the event is logged/notified + stored for **analytics** + shown on the dashboard.
   - **If confirmed:** deduct stock → alert OTO to pick up → WhatsApp customer "confirmed, courier coming."
4. **Cancellation:** customer may cancel **only before** admin confirms → notify customer **indirectly** (don't incentivize cancelling).

### Returns & exchanges — policy from current site (to replicate)
Source: retabstore.com policy. **Defect/damage-only** (matches food/perishable norms):
- **Eligibility:** ONLY for product **defects/damage** (عيوب / تمور تالفة). Excludes late receipt, shipping-company faults, and used/tampered products.
- **Window:** request within **3 days** of receiving the product → requires tracking **`delivered_at`** on orders.
- **Channel (current):** **WhatsApp** (returns dept +966 50 384 5356) with **photos** + order number + contact details.
- **Condition:** returned items in good condition with **original labels + packaging**.
- **Shipping fees:** **non-refundable** EXCEPT when the dates arrived **damaged**.
- **Resolution:** after inspection, exchange or **refund within 14 days**.
- **Build implication — returns module:** model as a **separate entity** (not just an order status): `return_requests` (order_id, user_id, status [requested/approved/rejected/exchanged/refunded], reason, resolved_at, admin_notes) + `return_items` (partial returns) + attached **photos** (media). Enforce 3-day window via `delivered_at`; refund via the payment gateway (card→Moyasar, Tamara→Tamara); shipping fee refunded only if damaged. Customer files in-account (with photos) → admin reviews → resolves; mirror WhatsApp touchpoints.
- **Also implies:** a **content/legal pages** capability (bilingual) for the policy page itself + about/contact (port Sky Amman's Site Content CRUD pattern).

### WhatsApp + Marketing — DECIDED: direct Meta Cloud API
- Use the **direct Meta Cloud API** (no BSP) — lowest cost, full control, under the same Meta Business Manager as the client's ads. We build the integration in Laravel (send + webhooks for delivery/read status).
- **Message types:** order confirmation / apology+suggest / "courier coming" / loyalty = **Utility** templates; monthly offers = **Marketing** templates (**opt-in required**). All business-initiated messages outside a customer's 24h reply window MUST be **Meta-approved templates** (free text only inside the 24h window).
- **Admin "marketing" section = two parts:** (a) **template manager** — compose + submit to Meta + track approval status (or manage templates in Meta Business Manager initially); (b) **campaign sender** — pick an approved template → fill variables → send to the opt-in segment → track delivery via webhook.
- **🔭 FUTURE IMPROVEMENT (deferred — auto-sync template approval status).** Today the template's "Meta approval status" (`draft/pending/approved/rejected` on `whatsapp_templates`) is a **manual mirror** of the real status in Meta Business Manager — templates are authored + approved THERE, and a human flips the flag here to match (the send guardrail `WhatsappTemplate::isApproved()` + the sender dropdown trust this flag but never verify it against Meta). If the manual step becomes error-prone, wire **Meta's Template Management API** to (a) **submit** templates to Meta straight from the `/admin/marketing` screen, and (b) subscribe to the **`message_template_status_update` webhook** so the local status flips to Approved/Rejected automatically. That removes the human sync step entirely (and the drift risk of a locally-"approved" template Meta actually rejects → per-message `failed` sends). Scope it when asked.

### Customers, accounts & engagement — DECIDED

- **Identity model:** `users` has **nullable** name/email/phone/password (a user may have only a phone, or only Google); a `social_accounts` table links providers to one account; `otp_verifications` for phone/WhatsApp sign-in.
- **OTP delivery = WhatsApp only (DECIDED)** — no SMS provider. Phone verification is via WhatsApp OTP; sign-in methods = **WhatsApp / Google / email**.
- **Reviews** (+ helpful votes; bilingual) and **wishlist** (per user) — reuse hardrock patterns.

### POS integration (SMACC / سماك) — NO API; daily Excel export→import (DECIDED)
- Physical store's POS is **SMACC** ("سماك" = how S-M-A-C-C is pronounced), by **Arab Sea Information Systems** (`arabsea.com`) — major KSA accounting/POS/inventory/e-invoicing platform.
- ⚠️ **Arab Sea confirmed: NO API integration.** Only path = **export SMACC inventory to Excel**, then **import into our admin** to re-baseline website stock.
- **Inventory model (DECIDED):** **SMACC = ledger of record**; website = **daily-synced mirror** + soft reservations for in-flight online orders. Website stock is **advisory** between imports; the **per-order admin confirm-step is the real backstop** (stale stock → at worst an apology, never a bad fulfillment).
- 🔑 **Critical rule:** online sales MUST be reflected in SMACC before each export, or every import "refills" already-sold units → upward drift + overselling. Website generates a **daily "online sales" report** so the admin batch-adjusts SMACC, then exports.
- **Daily routine:** (1) website → today's online sales; (2) admin reflects them in SMACC; (3) export SMACC → Excel; (4) import to admin (diff/preview → apply).
- **Import design:** match rows by stable key → products store **`smacc_sku`/barcode**; **diff/preview** before apply (flag unmatched rows); transactional; logged + undoable (reuse `ActivityLogService`); idempotent.
- **Mitigate the daily-commitment risk:** "stock last synced: Xh ago" indicator + banner/alert if no import in >24h; low-stock buffer; one-drag import. **Ask Arab Sea:** can SMACC schedule/email the export? → enables auto-ingest of the file (still not live sync).
- Knock-on: staler mirror → more out-of-stock rejections → more captured-card refunds (see Payments). Daily import keeps that low.

## Architecture Patterns (MUST FOLLOW)

These are the conventions we're adopting (most proven in Sky Amman). Where a pattern isn't built yet, it's marked **(to build / port)**.

### Inertia.js
- Controllers use `Inertia::render('page/name', [...props])` — no API routes for the storefront/admin UI.
- Mutations use `router.post/put/delete()` with `preserveScroll`, `onSuccess`, `onFinish`.
- Forms with files: native `FormData` + `forceFormData: true`.
- Routing is server-driven via `routes/*.php` — no client-side router.
- Auth state via `usePage().props.auth.user` (shared by middleware).
- Flash messages: server `->with('success', …)` → client reads `usePage().props.flash`.

### Bilingual (Arabic-first) + RTL — **(BUILT — foundation + storefront; deferred items below)**
- **Locale = server session, default AR** (single source of truth, no localStorage): `SetLocale` middleware → `app()->setLocale()`, `LocaleController` + `POST /locale/{locale}` (whitelisted `ar|en`), `locale` shared via `HandleInertiaRequests`. `<html dir>` is set from the locale in `app.blade.php` for correct RTL on **first paint** (no flash).
- **Client i18n = `react-i18next` + `i18next`** (`resources/js/i18n/{index,ar,en}.ts`, `lng`/`fallbackLng` = `ar`) + `LanguageContext` (`useLanguage()` → toggle does `fetch POST /locale/{lang}`, updates `document.dir`/`lang`; seeded from the shared session locale). Wired into **both** `app.tsx` + `ssr.jsx`; provider wraps the whole app.
- **DB content (`_ar`/`_en` columns):** controllers ship **BOTH** locales; the client picks via **`useLocalized()`** (`resources/js/lib/localize.ts`, AR fallback) so the toggle is **instant** — no server round-trip (mirrors Sky Amman). Stored content always wins over i18n fallbacks.
- RTL: use CSS **logical properties** (`text-start`, `ms-*`/`me-*`, `ps-*`/`pe-*`), not `text-left`/`flex-end`.
- **Server-side strings (BUILT):** flash + error messages go through `__('messages.*')` (`lang/{ar,en}/messages.php`, storefront **and** admin); Laravel validation/auth/passwords localized (`lang/ar/*` mirroring published `lang/en/*`, incl. AR field-name `attributes`). Resolved in the request's session locale. ⚠️ Server-rendered strings (these + product names) reflect the locale **at request time** — they follow on the next request, not the instant client toggle.
- **Brand web font (BUILT 2026-07-02, switched to Thmanyah 2026-07-18):** the storefront brand face is **Thmanyah Sans** (the ثمانية typeface), **self-hosted** WOFF2 replacing the old bunny.net **Tajawal**. Same wiring mechanism: override the Tailwind v4 token under RTL — `html[dir='rtl'] { --font-sans: 'Thmanyah Sans', ... }` + `--font-heading: 'Thmanyah Sans'` in `app.css` (the `font-sans`/`font-heading` utilities resolve the tokens, so the override cascades everywhere; no per-component changes). WOFF2 files live in `resources/fonts/` (weights Regular/Medium/Bold/Black), declared via `@font-face` with **`font-display: swap`**, fingerprinted by Vite (hashed URLs, `Vite::asset()`-resolvable — the manifest keys them by `resources/fonts/<file>.woff2`), and the Regular+Bold weights are **preloaded** in `app.blade.php` (`<link rel="preload" as="font" crossorigin>` — the `crossorigin` is mandatory or the browser double-downloads). ### Change Log + Revert — **(BUILT 2026-07-06 — v2 semantics)**
- **What:** staff audit history + per-entry **Revert** at `/admin/change-log`, backed by the existing `activity_logs` table + v2 columns `old_data`/`new_data`/`label`/`reverts_log_id` (migration `2026_07_06_100000`). - **Design — fixes Sky Amman's catalogued failure modes** (sky-amman CLAUDE.md → "ChangeLog / Revert semantics — compound-edit behavior catalog"): (1) **update snapshots are dirty-fields-only**, so reverting an old edit can never clobber newer edits to other fields; (2) **per-field conflict detection** — every field must still hold the entry's `new_data` value or the revert refuses with the diverged field list (also kills out-of-order resurrection); (3) **transactional reverts + honest `RevertResult` reason codes** — never a "success" that did nothing; (4) **reverts are first-class entries** — a revert writes a new semantically-typed row (`updated`/`deleted`/`restored`) linked via `reverts_log_id` and stamps the original ⇒ complete timeline and **redo = revert the mirror entry** (same machinery).

- **Usage:** updates pass `$before = $model->attributesToArray()` captured pre-save to `logUpdated()`; each write+log pair runs in `DB::transaction`. Adding a tracked section = call the right `log*` method + add the subject to `REVERTABLE`/`SUBJECT_LABELS` in the service.

### Building a designed section from a Figma composite — **(reusable recipe, distilled 2026-08-10)**

> Four About Us sections were built this way (hero, journey, values, why-us). **Measure the composite; do not eyeball it.** Every client-reported miss on these sections came from a value that was guessed, and every guess that looked right in code turned out wrong on screen. Follow the order below.

1. **Inventory the hand-off first.** Get dimensions and alpha of every file (`getimagesize` + an alpha histogram). Frames so far are all **1440×N**. An accompanying `.zip` has been an **empty 210-byte archive three times** — the real files always arrived loose alongside it, so don't debug the extraction. Filenames have twice contained a **non-breaking space (U+00A0)**, which is why Explorer silently skips them; check with `od -c`.
2. **If an SVG came too, read the geometry out of it** (`<rect>` x/y/width/height/rx, `<path fill>`). It is exact and beats any pixel measurement. But ⚠️ **Figma does not export effects to SVG** — a `fill="black"` rect whose PNG shows a white interior means an inset shadow or blur, and the SVG will also carry **zero `<text>`** because type is outlined, so copy must be rebuilt as live HTML.
3. **If the designer also supplied the bare background plate, diff it against the composite.** This is the highest-leverage trick available: agreement in a card-free region *proves* the plate is genuinely the background (why-us agreed to 0.17/255 in the gutter), and the difference then isolates the glass fill, the watermark, and the type, each measured **at the same pixel so the background gradient cancels**.
   - **Given an overlay asset instead of a plate, invert it: PREDICT the background and diff that.** Composite the supplied watermark over the flat page colour at a candidate placement and compare against the composite's background pixels. This turns "where does it go?" into a single number per hypothesis and settles it outright: contact-info's watermark scored **0.02/255** at natural size at (0,0) against 1.28 stretched, 3.45 mirrored and 3.08 absent, proving the designer had exported the already-rotated layer at frame scale. It also confirms the opacity for free (that asset is pre-faded to 7.9%, so it needs none of its own).
   - ⚠️ **When comparing the render back to the composite, compare a QUANTITY, not an impression.** Tint and coverage are independent: contact-info's watermark matched the design's tint at every size (12.9 vs 13.6 of 255) while covering only 16.5% of the visible background against 20.9%, because a vertically compressed section scales a height-anchored image down. Sweep the size, measure coverage at each step, and pick from the curve.
4. **Find element edges on scan lines chosen to be clear of type.** Generic step-detection locks onto glyphs and watermarks. Borders show up as sharp luminance spikes; sample *inside* a card, away from its text.
5. **Derive type size from ink, and only trust it when two independent dimensions agree.** Compute the size implied by the design's ink **width** and by its ink **height** (`canvas measureText` → `actualBoundingBox*` at 100px in the real font, then scale). ⚠️ They only agree on lines with **no kashida**; everywhere else the width figure is corrupted by the designer's elongation, so **height is the tatweel-invariant one**. In why-us the two no-kashida lines were the only usable anchors, and they proved the card title and body are the *same* size, with weight and colour carrying the hierarchy. Contact-info reached the same conclusion from three anchors (two Latin strings plus one un-elongated Arabic line, agreeing to 0.4px), and once the size was fixed **every one of seven strings matched the design's ink height to within 1px** — that agreement is the signal the whole spec is right, so compute it before writing any CSS.
   - **Ink height barely discriminates WEIGHT (a 5% spread across 400→900). Stroke thickness does.** Take the **median horizontal ink-run length** on scan lines through the middle of the x-height band, on the design and on canvas renders of the candidates. Contact-info's 18 / 6 / 3px stems mapped cleanly onto w900 / w700 / w400, which pinned a hierarchy the sizes alone could not (all three elements are ~the same size).
   - 🔴 **Use the SAME ink threshold on both sides or the comparison lies.** A strict "near the ink colour" test on the composite against canvas's 50% cut under-measured every design stem by ~1px, which pointed at Medium instead of Bold. **Nearest-colour classification** (is this pixel closer to the ink colour or the background colour?) is the 50% criterion and is directly comparable to canvas.
   - **Solve line-height from a two-line ink block:** `blockInkHeight = pitch + ascent(line 1) + descent(line 2)`, with the ascent and descent measured per-string in the real font. Cross-check on a second block — contact-info's two independent blocks agreed at 69.0 and 68.0px, i.e. 1.30.
6. ⚠️ **The composite's copy can be out of date, so decide per field where the value comes from.** Contact-info's email card reads `info@retabstore.com`, the **old Zid domain**, already wrong before the section was built. Anything the client can edit in the admin (here the phone and email, which the footer already reads from settings) must resolve at render time from that same source; only fixed display copy belongs in i18n. Transcribing a composite verbatim ships whatever was stale in it.
7. **Reproduce the constraint, not the numbers.** The values section's `181+376+326+376+181=1440` is exact yet unusable as a grid, because the columns were narrower than the text. What had to be preserved was the **element centres**; for a 2-column grid that is `(column + gap) / 2`, so the pair can be traded off freely. Ask what the number is *for* before copying it.
8. 🔴 **Compress the height. Every frame so far has been ~1136px, which cannot fit a laptop viewport once the 114px navbar is counted, and the client has flagged it.** Budget the frame first: if padding and gaps are a large share (values: 531 of 1136), halve them and scale type lightly; if the content dominates (why-us), the content has to scale too. Target **≲800px** and make every `clamp()` **cap at 1440px** so the section stops growing on larger monitors instead of scaling itself back out of view.
9. **Verify by measuring the render, not by looking at it.** Screenshot the section and run the *same* pixel analysis over it as over the composite, so the two are compared on identical terms. Then check the things a screenshot hides: section height and `scrollWidth > clientWidth` overflow **at 1920/1440/1280/1024/768/390 in both locales**.
10. **Recurring traps, all of which have already cost time here:**
   - **`text-end` is inverted in both locales at once.** It resolves against reading direction, so it means left in AR and right in EN. A heading almost always wants **`text-start`**.
   - **Physical vs logical positioning is a real decision.** Anything whose crop is baked to bleed off a specific corner (watermarks) must stay `left-0`/`top-0` in both locales; anything that should follow the reader uses `ps-`/`text-start`. Moving an absolutely positioned element into flow silently makes it direction-relative.
   - **Never use a negative z-index for a background image.** `position: relative` does not create a stacking context, so `-z-10` paints the image behind the nearest *ancestor* background and the section renders bare. Plain `absolute` first in DOM order plus a `relative` content wrapper is enough.
   - **Give any dark section a fallback `bg-` colour** sampled from its plate. White and gold type over a failed background image is an invisible section.
   - **Symmetric padding centres the em box, not the ink**, and Thmanyah reserves a large ascent for diacritics these labels never use. Correct with an asymmetric `--nudge`, measured by the **alpha-weighted pixel centroid** (the ink bounding box understates the error by more than half), and scope it per direction — Arabic needed 0.200em where English needed 0.065em.
   - **Kashida breaks string matching:** `'قيــــــمنا'.includes('قيم')` is **false**. Don't select or assert on elongated copy; and a fixed-width pill needs `whitespace-nowrap`, or a wrapping label grows the pill and spills past its rounded ends.
   - 🔴 **`ltr:` resolves against the element's OWN direction, not the page's.** Putting `dir="ltr"` on an element to stop RTL reordering a phone number or an email **also switches on every `ltr:` utility on that element** — in contact-info that silently gave two of the four cards the smaller English type size while the page was still in Arabic. Keep the `ltr:` size on the block and move the `dir` down onto the value's own `<span>`.
   - ⚠️ **A colour-keyed ink test inside a rounded rect measures the CORNER ANTIALIASING as ink.** With `rx=73` the naive scan reported each card's title as spanning the full 591px card width. Test membership of the rounded-rect interior (inset a few px) before classifying a pixel, the same way border scan lines have to dodge glyphs.
   - **One over-long English line does not just look wrong, it resizes the section.** With `auto-rows-fr` a single wrap grows *every* card in step: contact-info went from 797px to 910px on one 545px line in a 520px box. Budget the inner width, shorten the EN copy, and give English its own slightly smaller size so the copy has headroom rather than a 25px margin.
   - **PHP caches `stat()`**: after writing a file you already stat'd, `filesize()` returns the old value. `clearstatcache(true, $path)`, or compare md5.
11. **Ship copy as an array of objects in i18n** (`items: [{ key, … }]`), so a fifth card is a copy change rather than a code change, and **convert plates to WebP** (a 1.27 MB gradient PNG became **8 KB** at q84, verified at mean 0.724/255 with no pixel off by more than 3 — PNG is simply bad at smooth gradients). Copy already-lossy WebP **byte-for-byte** rather than re-encoding it.

### Coming Soon + Demand Capture — **(BUILT 2026-07-22)**
- **Purpose:** turn incomplete draft products (the Zid import left 22 hidden as `is_active=false`) into a demand funnel instead of dead weight. A draft can be surfaced on the store as **"Coming Soon"** — visible + describable but **not buyable**; customers tap **"I want this"** to register interest, which notifies staff for WhatsApp follow-up.

Framework support is real (`NotificationSender` honours `viaConnections`/`viaQueues`).
- **Admin emails are pre-rendered ENGLISH literals, not `__()`** — deliberate. The admin's panel language lives in their browser (localStorage + the `admin_locale` cookie), so a notification triggered by a **customer's** request has no way to know it, and a queued notification would otherwise capture the customer's AR session locale. The bell payload stays structured/client-rendered for exactly the same reason.
- **The bell is live without websockets:** `router.poll(45s, { only: ['notifications'] }, { keepAlive: false })` — an Inertia **partial** reload, so the server recomputes only the `notifications` closure (two indexed queries) and scroll/state are preserved for free; a hidden tab is throttled to one poll in ten ticks. Deliberately polling, not broadcasting — no Reverb/Pusher service to run. Plus a tab-title unread badge and an optional chime (WebAudio, no asset to ship; muted per browser under `admin.notifications.sound`).
  - ⚠️ **Gotcha — Inertia owns `<title>`.** It rewrites the title on hydration and on every navigation, so a badge written once (even one frame late via `requestAnimationFrame`) is silently dropped. The fix is a **`MutationObserver` on `document.head`** that re-applies the prefix whenever anything touches it, with an equality guard so our own write doesn't loop the observer.
- **WhatsApp transport is QUEUED** — `App\Jobs\SendWhatsappMessage` (`tries = 3`, backoff 30/120/600s). The ledger row is written synchronously as `queued` (so the admin log shows the attempt immediately) and only the Meta call is deferred; the job flips it to sent/failed and is idempotent (a retry after a landed send no-ops). Before this, every transactional send was an **inline HTTP call per recipient inside the customer's request** — seconds of checkout latency, and a transient failure lost the alert to a log line.
  - ⚠️ **Params are passed to the job, never read back off the row** — the ledger deliberately **redacts** sensitive params (OTP codes), so the stored payload is not a faithful send payload.
  - ⚠️ **OTP sends inline** (`dispatch(..., queue: false)`): the customer is staring at the code field, and it keeps plaintext codes out of the `jobs` table.
  - ⚠️ **The job rethrows to trigger retries, EXCEPT under the `sync` driver** (`$this->job?->getConnectionName()`), where the exception would surface inside the caller's request. A Meta outage must never break a checkout — that guarantee predates the queue and is preserved.
- 🔴 **DEPLOY PREREQUISITE — a queue worker MUST run in production** (`php artisan queue:work`, a second Railway service off the same image). `QUEUE_CONNECTION=database`, so without a worker the jobs table just fills: admin **emails**, **customer order emails** (receipt / confirmed / shipped) and **WhatsApp messages** would never send (the bell still works — that's what `viaConnections` buys). This is **not new** with these changes: `SendReviewReminder` (the 1-day-delayed review nudge) and `SendWhatsappCampaign` already depended on it silently.
- **History page — `/admin/notifications`** (BUILT 2026-07-30): the bell only carries the latest 10, so everything older was unreachable. Paginated own-notifications list with read-state + type filters, reached via **"View all"** in the dropdown (no sidebar entry — notifications belong to the navbar bell). Rows reuse the bell's open route, so clicking still marks read + redirects to the subject.
  - **Payload→text rendering is shared**: `components/admin/notification-content.tsx` (`useNotificationText()` + `iconFor()` + `NOTIFICATION_TYPES`), imported by BOTH the bell and the page, so a new notification type can't render in one and not the other. A hook rather than plain functions only so callers don't pass `t` around.
  - ⚠️ **Gotcha — the page paginator is called `entries`, NOT `notifications`.** `notifications` is the **shared bell prop** (`{unread, items}`); a page prop of the same name silently overrides it, and the bell's `items.filter(...)` would then throw on this very page. Pinned by `NotificationBellTest::test_history_does_not_shadow_the_shared_bell_prop`.
  - Type filter uses a JSON-path where on the structured payload (`where('data->type', …)`, whitelisted so it's never raw input) → `json_unquote(json_extract(...))`. **Verified on SQLite (tests) AND MariaDB 10.4 (dev)**; MySQL 8 (prod) is strictly better.
- **Mail provider = Resend (WIRED 2026-07-30).** `resend/resend-php` installed (the framework's `ResendTransport` needs it for `Resend::client()`); `config/mail.php` already had the `resend` mailer and `config/services.php` the `RESEND_KEY` binding, so no config changes were needed. Verified with a real send to Resend's simulator (`delivered@resend.dev`).
  - **The client's key is SEND-ONLY (restricted)** — good practice, but it means it can't read any other endpoint. `GET /domains` answers **401 `restricted_api_key`**, which `App\Support\ResendProbe` treats as **OK** (an invalid key answers **400 `validation_error`** instead, and a full-access key answers 200 with each domain's verification status — three cleanly distinguishable states). Reported by `integrations:check` alongside the payment providers.
  - 🔴 **Remaining step: verify `retabstore.com` in Resend** (add the domain, paste DKIM/SPF into Cloudflare DNS). Confirmed empirically — sending from `no-reply@retabstore.com` today fails with *"The retabstore.com domain is not verified"*. **Until then the only accepted from-address is `onboarding@resend.dev`**, which is what `.env` uses.
  - **Dev deliberately stays on `MAIL_MAILER=log`.** The seeded dev staff use fake `@retab.com.sa` addresses, so pointing dev at Resend would bounce them off a brand-new account and dent its sending reputation. `php artisan mail:test <address>` sends through the **resend** mailer explicitly (`--mailer=` to override), so a real send never requires flipping the global default. Production sets `MAIL_MAILER=resend`.
  - ⚠️ Mail is **queued** (see `viaConnections` above), so nothing sends without the worker.

### Customer-facing email — **(BUILT 2026-08-03)**
Everything above is STAFF alerting. Customers now get their own mail, and the design decisions are close to the inverse of the staff ones.
- **Three emails, one per lifecycle beat:** `OrderPlacedMail` (the receipt), `OrderConfirmedMail`, `OrderShippedMail` (carrier + tracking) — `app/Mail/`, all extending **`OrderMail`**, all `ShouldQueue`. Sent through **`App\Services\CustomerMailer`** (`orderPlaced/orderConfirmed/orderShipped`), shaped after `WhatsAppService`: call sites state what happened, and every "can we reach this customer?" decision lives in one place. Returns a bool so callers/tests can assert rather than guess.
- **Where they fire:** confirmed + shipped sit beside the existing WhatsApp calls in `Admin\OrderController`. **Placed is split by payment method on purpose** — bank transfer sends at checkout (`CheckoutController`, ⚠️ *after* the `payment_method` update, since the mail reads it to decide on the bank block), while **card/Tamara send on payment confirmation** (`PaymentService::markOrderPaid`, `TamaraService::markAuthorized`), never at checkout: a customer who merely reached the hosted gateway and abandoned it must not get a receipt for an order that was never paid.
  - ⚠️ **Idempotency differs between the two gateways.** `markOrderPaid` already early-returns when the order is paid, so a repeated webhook can't double-send. **`markAuthorized` had no such guard** and re-runs on every delivery attempt — it now captures `$firstAuthorization` (was the order still `pending_payment`?) before the write and only mails on that transition.
- 🔑 **Language: `orders.locale`, snapshotted at checkout** (new column, migration `2026_08_03_100000`). This is the whole reason the base class exists. The mails are **queued**, so at render time `app()->getLocale()` is the WORKER's locale (AR, the app default) — an English shopper would silently get an Arabic receipt. `OrderMail::__construct` pins `$this->locale` from the order; Laravel wraps both the envelope and the view render in `withLocale`, so **the subject line follows too**. Guests have no user record to read a preference from, which is why this is on the order and not on `users`.
  - ⚠️ **Testing gotcha:** asserting the subject by calling `envelope()` **directly** bypasses that wrapper and resolves `__()` in the ambient locale — a correctly-localized subject then looks broken. Use **`assertHasSubject()`**, which goes through the same path a real send does. Pinned in `CustomerEmailTest`.
- **Templates are hand-rolled, not Laravel's markdown theme** (`resources/views/components/mail-layout.blade.php` + `emails/*.blade.php` + a shared `partials/order-summary`): the store is Arabic-first and the whole document has to flip, which means fighting the published theme's LTR-baked CSS on every component. Table layout + inline styles only (Outlook ignores flex/grid, several clients strip `<style>`); `dir` is set on `<html>` **and** the outer table because Gmail drops `<html>` attributes when it re-wraps the body; **no web fonts** (Thmanyah is licensed for embedding on our own origin, not for redistribution through mail clients). Copy lives in `lang/{ar,en}/emails.php`. IBAN / account / tracking numbers are pinned `direction:ltr; unicode-bidi:embed` so RTL reordering can't visually scramble a number mid-copy.
- **Why the receipt matters most for bank transfer:** it's the one method with no gateway receipt of its own, and the IBAN plus the order number the customer must quote as the transfer reference otherwise exist only on a page view that's gone the moment they close the tab.
- ⚠️ **`customer_email` is nullable and that's normal** — phone-only accounts (WhatsApp OTP) and guest checkout only require a phone; those customers are reached over WhatsApp, so no address is a silent no-op, not an error. Falls back to the account address when the order snapshot has none.
- ⚠️ **Guests get no "View your order" button.** The storefront gates `/orders/{number}` on session state, so a link opened days later in another browser would 403. The body carries everything they need instead. _Follow-up if wanted: a signed URL would let guests back in._
- **Deliberately deferred:** return-status emails (the returns flow has four WhatsApp touchpoints and its own status vocabulary — a second template family, not a variant of these).
- **Preview them** by rendering a mailable to HTML in tinker (`(new OrderPlacedMail($order))->render()`); there's no preview route.
- **Not built yet** (ranked next steps): alerts for **Tamara authorizations nearing expiry** (money — auths expire in 24-48h; the dashboard already computes `tamaraExpiring`, so it's a scheduled command away — but it would be the project's FIRST scheduled task ⇒ a `schedule:work` service) and low-stock / sync-gone-stale; **per-recipient routing** (admin phones/emails are env-only today, and every staff member gets everything).

### SEO — **(BUILT — sitemap/robots/JSON-LD 2026-07-02; 301s + slug cleanup 2026-07-25)**
- Storefront SEO matters (organic product discovery). Server-render public pages (enable SSR — see Build Progress), per-page/per-product `<Head>` meta + OG, dynamic `sitemap.xml`, `robots.txt` disallowing admin, JSON-LD (`Product`/`Offer`/`BreadcrumbList`), and `hreflang` AR↔EN. _(hreflang deliberately skipped — session-based locale shares one URL per language; see the 2026-07-02 Build Progress entry.)_
- **301 redirects from the old Zid URLs + slug cleanup — BUILT 2026-07-25 (run `catalog:clean-slugs --apply` on prod AT LAUNCH).** _Why it matters:_ the live Zid store is already indexed by Google; each ranked result points at an old Zid slug. Zid used the **same** `/products/{slug}` path we do (verified: `retabstore.com/products/{old-slug}` → 200), and the importer seeded our `products.slug` **from** `old_zid_slug` — so today the old URLs already resolve. The moment we clean a slug, its old URL would 404 and the ranking (link equity) is lost. _What was built:_
  - **`redirects` table** + `App\Models\Redirect` (`from_slug` unique, nullable `product_id` FK, static `to_url` fallback, `status` default 301, `hits`). `target()` resolves to the product's **current** slug (so a later re-clean still lands right) or the static URL, else null → 404.
  - **`catalog:clean-slugs {--apply}` command** — dry-run by default. Regenerates only **junk** slugs (ar-prefixed / English / uppercase / leading-hyphen — detected as "contains a Latin letter or leading `-`") into clean **Arabic** slugs from `name_ar` via **`App\Support\ArabicSlug`** (preserves Arabic + Arabic-Indic digits, strips tatweel/harakat, lowercases Latin; Str::slug would transliterate Arabic away). Already-clean Arabic slugs are **left untouched (no redirect)** → fewest redirects, best ranking preservation. Records a 301 from each changed slug; transactional; idempotent (cleaned slugs aren't junk on re-run; `firstOrCreate` redirects); dedupes collisions with `-2`. On the real catalogue: **27 of 87** slugs cleaned.
  - **Resolution:** the `/products/{product:slug}` GET route has a **`->missing()`** hook → `RedirectController@missingProduct` (301 to `target()`, increments `hits`, else 404). Non-breaking (keeps the `{product:slug}` binding; `route('shop.product', …)` still generates by slug) and **`route:cache`-safe** (the missing closure serializes via `SerializableClosure` — verified). Chose Arabic slugs over English (client decision 2026-07-25).
  - **Launch step:** after final slugs are settled, run `php artisan catalog:clean-slugs` (preview) then `--apply` **on prod**. Future legacy paths (e.g. old category URLs) can be added as manual `redirects` rows (set `to_url`). _Deferred:_ the 16 Zid **variant-parent** URLs (indexed but not 1:1 with a product) — add hand-mapped `redirects` rows if they show in Search Console.
- **Brand assets: favicons, PWA manifest + OG share card — BUILT 2026-08-08.** `public/` now carries `favicon.ico` (multi-res 16+32, hand-assembled — PHP GD cannot write ICO, but the format accepts raw PNG blobs: 6-byte header + 16-byte directory entries + payloads), `icon.svg`, `apple-touch-icon.png` (180), `icon-192.png`, `icon-512.png`, `icon-maskable-512.png`, `site.webmanifest` (theme `#1b4e53`), and `og-image.{jpg,webp}` (1200×630). Linked from `app.blade.php`. _Prior state: `public/favicon.ico` was the scaffold's **0-byte** placeholder and there were **no icon links at all**, so the site had no favicon anywhere and no default share card._
  - 🔴 **THE GOTCHA THAT MATTERS: Inertia `<Head>` tags do NOT exist in the server HTML unless SSR is running.** They are applied client-side after hydration, and **WhatsApp's and Facebook's link-preview crawlers do not execute JavaScript** — so with SSR off, every `og:*` tag on the site is invisible to them and shared links preview blank. Verified empirically here: `curl` with SSR off returned only the Blade-level tags; with the sidecar up, all seven `og:*`/`twitter:*` tags appeared with `data-inertia`. **This promotes the SSR sidecar from a performance nicety to a hard requirement for the store's main marketing channel.**
  - ⚠️ **A running SSR sidecar keeps serving the OLD bundle after a rebuild.** Cost real debugging time here: `npm run build` refreshed `bootstrap/ssr/ssr.js`, but a sidecar left running from an earlier session still rendered the previous markup (new tags missing, old ones present — which looks exactly like a broken code change). A second `node bootstrap/ssr/ssr.js` **crashes with `EADDRINUSE` on 13714 rather than taking over**, so the stale one silently wins. **On deploy, the SSR service must restart too** — redeploying only the web service leaves stale markup being served.
  - **`og:image` is deliberately NOT in `app.blade.php`.** A layout-level tag renders *before* `@inertiaHead`, and crawlers treat the **first** `og:image` as primary, so it would override the product page's own photo. Instead the absolute URL is a shared Inertia prop (`ogImage`, built from `APP_URL` server-side because crawlers do not resolve relative paths) consumed by each page's `<Head>`; the product page falls back to it only when a product has no photo.
  - **The JPEG twin is intentional.** WhatsApp's preview crawler is unreliable with WebP and WhatsApp is this store's primary channel, so `og:image` points at `og-image.jpg` (113 KB) while the WebP is kept alongside it.
  - ⚠️ **Designer hand-off gotchas (both cost time):** every exported icon was **one pixel oversized** (17/33/181/193/513 — a Figma fractional-frame rounding artifact) which makes browsers resample favicons and makes Chrome reject a maskable icon for a declared-vs-actual size mismatch, so all were resized to exact powers; and two filenames contained a **non-breaking space (U+00A0) instead of a space**, which is why Windows Explorer silently skipped them during extraction (leaving an empty `SVG/` folder that looked like a corrupt archive) and why any hardcoded path with a normal space fails to match. The archive was fine — .NET extracted it perfectly. Also, the master SVG's viewBox was **not square** (1133.94×1341.15), which browsers letterbox in a square favicon slot, so it was widened to `-103.605 0 1341.15 1341.15` (centres the artwork without touching a path).
  - 🔑 **Transparency is deliberately NOT uniform across the set** (designer supplied a transparent PNG set on 2026-08-08; the original white-backed one is only kept where opacity is required):
    - `favicon.ico` (16+32), `icon.svg`, `icon-192.png`, `icon-512.png` → **transparent**, so the mark sits correctly on both light and dark browser chrome.
    - `apple-touch-icon.png` → **flattened onto white**. iOS composites a transparent home-screen icon onto **black**, which would put the gold mark on a black tile instead of the intended white one.
    - `icon-maskable-512.png` → **the designer's original white-backed export, kept as-is**. A maskable icon must be opaque *and* keep its content inside the inner-80% safe zone because Android crops it to the launcher's shape; that export already has the padding, so synthesising one from the plain transparent icon would risk cropping the mark.
    - Rebuilt with plain GD (`imagecopyresampled` + the `imagealphablending(false)`/`imagesavealpha(true)` recipe) so alpha survives the downscale; transparent PNGs also compress better, which took `favicon.ico` from 2208 to 1457 bytes.

## Code Quality Rules (adopted from Sky Amman)

- If a model has a dedicated method (`Media::storeFile()`, `Setting::set()`), **always use it** — never bypass with raw `::update()`/`::create()`.
- The same write (create/update/restore) must go through one shared model method.
- **Never query inside a loop** — batch-fetch with `whereIn()`/`pluck()` first. Paginated views query related data only for the current page's IDs.
- Guard no-op operations (short-circuit when nothing changed).
- If a method returns a meaningful value (bool/count/status), use it — don't call-and-ignore.
- Match the surrounding code's style, naming, and comment density.

- **⚠️ Composer gotcha — `composer update <package>` can silently install a DEV branch and "fix" nothing (hit 2026-07-30).** _Symptom:_ `composer update guzzlehttp/guzzle` reported `Upgrading guzzlehttp/guzzle (7.12.3 => 7.12.x-dev 9aa17bc)` — a **dev-branch commit of a production HTTP library** — and `composer audit` still listed the same 4 advisories afterwards. _Root cause (two things combined):_ (1) the starter kit ships **`"minimum-stability": "dev"`** (with `prefer-stable: true`), so dev branches are *allowed* whenever no stable version satisfies the resolution; (2) `composer update <one-package>` deliberately **will not touch that package's own dependencies** — guzzle ≥7.15 requires `guzzlehttp/psr7 ^2.13` + `guzzlehttp/promises ^2.5.1` (installed: 2.12.3 / 2.5.0), so the stable target was unreachable and composer quietly settled on the highest thing it *could* take: the 7.12 dev branch. > - 🔑 **The finding: the visitor's IP is not in `X-Forwarded-For` at all on this stack, so no `trustProxies` value could ever have fixed it.** Railway's edge **replaces** whatever XFF arrives with its own chain, `<ip that connected to Railway>, <Railway edge hop>`. With Cloudflare in front that reads `<Cloudflare egress IP>, <Railway edge IP>` — the visitor appears nowhere. Meanwhile `trustProxies(at: '*')` does **not** mean "trust anything": Laravel maps it to `setTrustedProxyIpAddressesToTheCallingIp`, i.e. **REMOTE_ADDR only** (the `100.64.x.x` private hop). Symfony then filters trusted entries out of the chain, `array_reverse`es what's left and returns index 0 — the **rightmost untrusted** entry, which is a Railway edge IP. > - **Impact, in the app's own terms:** each rate limiter keys on the client IP, so all visitors through one Railway edge node shared one counter. (b) A forged **`CF-Connecting-IP`** on that same direct request **passed through untouched** and did *not* influence `X-Real-IP` — Railway only honours Cloudflare's header when the connection genuinely comes from Cloudflare. > **Last updated:** 2026-08-10 — 🔴 **Third and final instance of the navbar blank-strip bug: a fast scrollbar drag exposed up to 94px of page background.** Client-reported. One-line fix in `navbar.tsx`, but the lesson is bigger than the line.
> - 🔑 **The rule was already right; it was being applied to the wrong quantity.** The safety guard compares the header's translate against the scroll position, but it read `offset` — the last **target** — instead of where the element actually **is**. Those two are identical only while nothing is in flight. During the reveal's 750ms `transition-delay` they disagree by the *entire* travel band, because the element has not moved at all yet.
> - **Why a scrollbar drag specifically, when a wheel is fine.** The drag's first event lands while still far down the page, which earns the reveal, sets the target to 0 and starts the delay. Every later event in the same drag then sees `offset === 0`, so the guard's `offset > y` term is false **forever**, and the header sits parked off-screen while the scroll position falls inside the band. A wheel cannot reach the top inside 750ms; a drag (or a scrollbar-track click) can. **Measured before the fix: 54px of `DIV.flex.min-h-screen` at the viewport top at y=60, 94px at y=20**, for the remainder of the delay.
> - **Fix:** read the rendered translate (`-header.getBoundingClientRect().top`) instead of the cached target. ⚠️ That is a layout flush, so it is read **only when `y < band`** — past the band the value is capped at `band <= y`, so no amount of transition lag can violate the invariant and the cached target is a fine stand-in. Confines the read to the first ~114px of the page.
> - 🔑 **Against the rendered value the guard becomes provably complete rather than merely careful:** `next` is always `0` or `min(y, band)`, hence always `<= y`. So a violation (`rendered > y`) implies `next <= y < rendered`, which *is* the guard's condition. **Every violation is therefore corrected in the frame it appears** — there is no longer a class of scroll input that can slip past, which is what the two previous fixes could not claim.
> - ⚠️ **Worth internalising for any lag-based animation:** a "current position" variable that is really a *target* is a silent lie whenever a transition has a delay. Behaviour is now two states: pinned open within 24px of the top, hidden by one downward scroll, revealed full by scrolling up. ⚠️ **Anything that reintroduces an in-flow height change here** (a collapse, an announcement bar) brings the artifact straight back; animate colour/shadow/opacity instead. **Unexpected bonus:** scroll events per 300px gesture dropped from **15 to 1** — the anchoring loop had been generating ~14 spurious events per scroll, so this was a real jank source, not just a visual nit.
> - 🔴 **Follow-up the same day — the hide exposed a blank strip, and the constant height made it worse.** _Symptom (client-reported):_ a white band above the hero on scroll down. _Cause:_ `sticky` keeps the header's box in **normal flow**, and a transform does not remove that box, so translating it away while the viewport is still inside the box just reveals the box. Proven with `elementFromPoint(x, 5)`: at `y=60` the topmost element was the page wrapper, not the hero; from `y=140` it was hero content. Pinning to a fixed 130px height had made the strip **130px instead of the old compact 90px**, so the previous change amplified a pre-existing flaw. _Fix:_ the pinned band is now the header's **measured `offsetHeight`** (cached, re-measured on resize — reading it per scroll frame would force a layout flush), so the header only hides once hiding reveals real content. This adapts across breakpoints for free: desktop ~130px (two rows) vs mobile ~81px (row 2 is `md:flex`), where a fixed number would either leave a desktop gap or over-pin on mobile. ⚠️ **Consequence to accept:** on desktop one 120px wheel notch no longer hides it (120 < 130) — the header cannot hide sooner without exposing its own box. The alternative is running the hero *underneath* an overlaid header, which was tried and rejected in the abandoned slide-in experiment. Verified gap-free at 1400px **and** 390px, plus a screenshot of the hero flush to the top edge. _Verified by measuring `scrollY` / header `top` / height / opacity at each wheel notch (not by eyeballing):_ `y=0` FULL → one notch → HIDDEN → scroll up → FULL, height constant at 130px throughout, plus **28/28 E2E green**, `tsc` ✓, eslint ✓, Prettier ✓.
